# Technology Stack, Compatibility, and Cost

These are architecture choices, not a dependency installation list. The actual GM 5 Plus must decide any performance-sensitive option. “Free” below means no required service fee under the stated setup; it does not mean zero electricity, hardware, internet, or guaranteed future API quota. Source links are primary vendor/project documentation checked for this design; recheck versions, model availability, and pricing before implementation.

## Baseline choices

| Technology | Why it fits and where it runs | API 24 / resource / offline / cost | Alternative and decision trigger |
| --- | --- | --- | --- |
| Kotlin + Android SDK + Canvas | Preserve the working `FaceView`, `FaceAnimator`, `FaceBehavior`, native touch and voice lifecycle. No UI framework rewrite. | App `minSdk=24`; modest draw allocation, ~30 fps only during motion, no network needed for face. Existing code confirms this rather than a vendor benchmark. | Add custom drawable elements only if a specific expression needs them; do not introduce Compose or a game engine for two eyes. |
| `AudioRecord`, 16 kHz mono PCM | Existing capture and silence stop; can feed a PCM-based offline recognizer. | Native API on the target; 15 s at 16 kHz 16-bit mono is about 480 KB PCM before temporary buffers. Offline capture, no service fee. The current RMS threshold is a simple VAD and needs noise tests. | Platform speech service owns its microphone session, so it needs a separate adapter rather than consuming this buffer. |
| Android `TextToSpeech` | Existing `SpeechOutput` implementation, Turkish default, stop/shutdown callbacks. | API 24 supported; actual installed voice may be network-backed. Check `Voice.isNetworkConnectionRequired()` and test offline playback on the phone. No app API fee; voice download/availability varies. [Android TTS](https://developer.android.com/reference/android/speech/tts/TextToSpeech), [voice selection](https://developer.android.com/reference/android/speech/tts/TextToSpeech.Engine). | A local host TTS engine or explicit cloud TTS only if Turkish quality is inadequate; measure CPU, latency, privacy, and cost first. |
| Node.js 22 single Docker container | Reuse `backend/Dockerfile` and provider adapters; no additional runtime npm dependency today. | Runs on the owned Mac, not on the phone. Can serve local logic offline, but Gemini calls need internet and an available free quota. Docker Desktop is not the only portable host; Linux Docker is possible. | A Raspberry Pi or another small computer can host the same container after performance tests. No Kubernetes/microservices. |
| Current provider adapters | Gemini, OpenAI, Anthropic, and explicit mock use one normalized backend interface; keys stay server-side. | Android API level irrelevant. Gemini free tier is conditional and can change; OpenAI/Anthropic are optional and may cost money. No automatic paid fallback. [Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing). | Add a local LLM adapter only after a specific Mac/Pi model meets Turkish quality and latency targets without starving STT. |

## Real Turkish speech recognition decision

| Candidate | What is verified | Cost/offline and resource implications | Decision |
| --- | --- | --- | --- |
| Android platform `SpeechRecognizer` | API available well before 24; callbacks/lifecycle and `destroy()` are documented. `EXTRA_PREFER_OFFLINE` exists from API 23 but an implementation may ignore it. The service may stream audio. The app now uses it through `PlatformSpeechInput`. [SpeechRecognizer](https://developer.android.com/reference/android/speech/SpeechRecognizer), [offline hint](https://developer.android.com/reference/android/speech/RecognizerIntent). | No app-side API fee; **not guaranteed offline or private**. Turkish service and language pack availability depend on the GM 5 Plus installation. The adapter has not yet been validated on that device. | Implemented as default input. Still test Turkish service support and Wi-Fi-on/off behavior, then quantify errors and latency. Never label it offline solely because the hint is set. |
| Vosk small Turkish model | Official list offers `vosk-model-small-tr-0.3`, 35 MB, license Apache 2.0; Vosk documents small models around 300 MB runtime and offline Android use. Its Android demo declares minSdk 21 and ARM64 ABI. [Models](https://alphacephei.com/vosk/models), [Android demo](https://github.com/alphacep/vosk-android-demo/blob/master/app/build.gradle). | Truly offline, no API fee; adds native library/model storage and substantial RAM versus current app. Published Turkish error rate is TBD, so quality is unproven. Model distribution/update and exact native ABI/dependency compatibility need a GM 5 Plus build test. | Preferred fallback if platform recognizer lacks dependable Turkish/offline behavior. Benchmark cold start, peak RSS, latency, battery, desk-noise accuracy; do not bundle it until those gates pass. |
| Vosk or whisper.cpp on Mac | Local host can process consented audio without phone model RAM pressure. Vosk has a small Turkish model; whisper.cpp may offer quality but CPU and model size depend heavily on the Mac. | Offline recognition when Mac is on, no service fee; LAN transport must be authenticated before sensitive audio. The existing `HttpSpeechRecognizer` requires HTTPS and the backend has **no STT endpoint**, so a new adapter/route would be needed. | Optional if on-device engines fail; benchmark the actual Mac. Do not claim it works on the phone or meets latency without measurement. |
| Cloud STT | Existing Android interface accepts an independently configured HTTPS PCM-to-JSON service. | Network-dependent, privacy exposure, possible usage/billing costs; no provider is configured by default. | Opt-in only, with explicit price and data-retention review. Not part of the zero-cost baseline. |

The initial voice path remains push-to-talk. Always-on wake-word processing is a separate privacy/battery project, not a prerequisite. A better local VAD can be introduced behind the recorder interface after recordings from quiet/noisy desks show the present fixed RMS threshold is insufficient. Do not retain those test recordings without explicit consent and deletion rules.

## State, memory, and messaging

| Choice | Suitability and cost | Limit / alternative |
| --- | --- | --- |
| Typed in-process events + single reducer | Android Robot Core can serialize state changes on the main thread and dispatch work off-thread; no dependency or service fee. Node modules can use direct calls/events. | Avoid a global untyped event bus. Add queue bounds and session IDs before sensors/autonomy. |
| Existing `SharedPreferences` for last eight messages | Preserves current context and simple rollback; small bounded JSON. Native/offline/free. | Not a searchable or multi-layer memory store; no fine-grained deletion UI. Do not extend it indefinitely. |
| SQLite on the Mac for future durable memory | One local file with transactions, indexes, retention, and export; offline/free. The backend should own the only durable robot memory. | Choose a **tested stable Node binding** and backup method in phase 5. Node 22's built-in `node:sqlite` is still marked experimental, so it is not selected as a production foundation yet. [Node 22 SQLite status](https://nodejs.org/download/release/latest-jod/docs/api/sqlite.html). Android SQLite is available if an on-device-only memory mode is later required. |
| SQL/FTS5 retrieval first | Structured facts and modest text history should fit indexed queries and a small context budget without an embedding service. | Verify FTS5 in the selected SQLite build. Add vector search only after quality and resource measurements justify it. |
| REST/JSON for turns and configuration | Already implemented and easy to test; request IDs and bounded timeouts exist. Offline locally only while Mac is available. No added infrastructure. | WebSocket later for measured real-time telemetry; do not move ordinary conversation requests to streaming without a latency need. |
| WebSocket (conditional) | One bidirectional channel could carry bursty sensor/gesture updates and acknowledgments. | Requires heartbeat, backpressure, reconnect snapshot, and auth. Not required for phase 1 or simple sensor reads. |
| MQTT (deferred) | Espressif supports MQTT for publish/subscribe, useful with multiple independent devices. [ESP-MQTT](https://docs.espressif.com/projects/esp-idf/en/v5.4/esp32/api-reference/protocols/mqtt.html). | A broker adds operational state/security. Start with bounded direct command/status transport for one ESP32; add MQTT only after scale/event evidence. |

## Vision and physical interface

| Technology | Fit, compatibility, cost | Boundary |
| --- | --- | --- |
| Android Camera2 | Platform API from 21, so API 24 is possible. Low-rate frame acquisition avoids a large camera UI dependency. [Camera2](https://developer.android.com/reference/android/hardware/camera2/package-summary). | More device-specific code than CameraX; inspect camera capabilities, heat, and battery on the GM 5 Plus. No camera use until permission and an obvious active indicator are implemented. |
| CameraX (alternative) | Official library supports API 21+ and simplifies device quirks. [Android camera library choice](https://developer.android.com/media/camera/choose-camera-library). | Adds library weight. Choose it if Camera2 reliability cost exceeds the app-size/memory cost; benchmark both. |
| Local motion detection | Sparse downscaled luminance-frame difference is feasible to prototype without ML. | It is not person or object recognition; avoid claiming identity. No always-on feed in the first vision phase. |
| ESP32 + ESP-IDF + motor driver | Open SDK, Wi-Fi, local HTTP server and PWM control; safety firmware independent of cloud. [HTTP server](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-reference/protocols/esp_http_server.html), [motor PWM](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-reference/peripherals/mcpwm.html). | Requires **purchased or already-owned** board, power supply, motor driver/servos and mechanical parts. ESP GPIO must not directly power motors. MCU cannot run the Android face or a general LLM. |
| BLE (alternative transport) | Could remove Wi-Fi dependency for a nearby phone/ESP pair. | Pairing, reconnection, Android vendor behavior, and message-size limits add complexity. Defer until a Wi-Fi prototype demonstrates a concrete gap. |

## Security and operational cost gates

1. Current Compose port is selected Mac LAN IP and `backend/.env` is ignored/excluded from the image. The backend has per-IP rate limiting but no client authentication; LAN HTTP is plaintext. Treat this as a trusted-network development setup, not a security boundary for personal memory or motors.
2. Before long-term memory or remote tools, design pairing and authenticated transport. A self-signed local TLS certificate with Android pinning costs no service fee but needs certificate rotation and recovery UX. Test on API 24. Never solve this by placing a reusable secret in source, the APK, or a public URL.
3. A provider's free tier is a changing external policy, not a stable zero-cost guarantee. Enforce a local call budget and a hard “no paid fallback” setting. If quota ends, use face/local responses and report the limitation. Never activate billing automatically.
4. Cost is **0 TL ongoing software/service** only when owned Mac/phone, local processing, and currently available free API quota suffice. Electricity, internet, backup media, added electronics, and optional provider bills remain outside that claim.
